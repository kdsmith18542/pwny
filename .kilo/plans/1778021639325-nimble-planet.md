# Plan Review: Pwny Development Plan + Auto ML Mode

## Summary

The submitted 11-phase plan is the strongest piece of strategic thinking in this repo. It defines a clear identity, avoids the traps that kill security tool projects, and sequences work correctly (MSFRPC bridge before native exploits, recon import before exploitation, GUI after API stability). 

The core question: should we add a "full auto toggle" for ML-driven review, targeting, and chaining?

**Answer: Yes, with strict guardrails. But not as "Auto" mode — as "Chain with Approval" and "Auto Low-Risk Only" as two separate features.**

## Auto ML Toggle: Analysis

### What the User Is Asking For

Three capabilities behind one toggle:

1. **ML Auto Review** — imported recon data → ML summarizes, groups, detects interesting services, generates suggestions (WITHOUT executing)
2. **ML Auto Targeting** — given suggestions, ML selects targets and modules (WITHOUT executing)
3. **ML Auto Chaining** — ML runs a sequence of modules automatically, using results from step N to decide step N+1

### Risk Analysis

| Capability | Risk Level | Primary Concern |
|---|---|---|
| ML Auto Review | Low | Hallucination (ML invents services/hosts that don't exist). Mitigated: ML output is tagged as "assistant review" not "fact." |
| ML Auto Targeting | Medium | ML picks a prod host because its OS fingerprint matches the lab target. Mitigated: scope rules must be set first. Non-scope hosts rejected at runtime. |
| ML Auto Chaining | High | A sequence of safe modules combined can produce dangerous results (e.g., cred scan → valid creds → ML tries to use them on DC). Also: infinite loops, rate limits, DoS of target. |

### Recommendation: Two Separate Features, Not One Toggle

**Feature A: "Auto Suggest" (low risk, ship in Phase 5-6)**

This is essentially the plan's existing "Suggest All" safety mode with one addition: ML can auto-generate suggestions without the user clicking "generate." It replaces:

```
User imports recon → User clicks "generate suggestions" → ML reviews → User sees list
```

With:

```
User imports recon → ML reviews automatically → Suggestions appear in panel (no execution)
```

Guardrails:
- Suggestions have `source: ml_auto` tag to distinguish from rule-based
- ML suggestions have lower default confidence than rule-based
- User still must approve each suggestion individually
- Can be toggled on/off per workspace

**Feature B: "Semi-Auto Chain" (medium risk, ship in Phase 7-8)**

This is what the user means by "chaining." Key: ML plans the chain, user approves the chain (not individual steps), but there are runtime guardrails.

The model:

```
1. ML analyzes host X → proposes 5-step recon chain
2. User sees chain preview:
   ├── Step 1: portscan (safe, passive)
   ├── Step 2: smb_version (safe, low noise)
   ├── Step 3: smb_enumshares (safe, medium noise) 
   ├── Step 4: smb_login with cred list (RISKY — may lock accounts)
   └── Step 5: hashdump (POST-EXPLOIT — requires session)

3. User can:
   - Remove steps (e.g., delete step 4 and 5)
   - Reorder steps
   - Set breakpoints (stop after step 3 and ask)
   - Adjust options per step
   - Set risk cap ("only auto-run low risk")
   - Set timeout per step
   - Set auto-stop conditions ("stop on first failure", "stop if session obtained")

4. User approves chain → Pwny executes with runtime guardrails:
   - Scope check before each step
   - Auto-stop on unexpected output matching danger patterns
   - Auto-stop if a step fails (configurable)
   - Every step logged individually with timing
   - Can be paused/resumed
   - User can abort at any time from GUI
```

**Feature C: "Full Auto" (DO NOT SHIP)**

Full auto where ML autonomously selects targets, chooses exploit chains, and executes without human review of the chain should NOT be built. Even with warnings, it:

1. **Violates the project's stated principle**: "Human-approved workflows"
2. **Creates legal liability**: "The tool did it" is not a defense
3. **Damages credibility**: Security professionals will not trust a tool that auto-exploits
4. **Is the wrong user**: The user who wants full auto is not the user this plan targets (professional pentesters, consultants, educators)

### How to Implement "Auto" In the GUI

The plan's safety modes should become:

```
Off                    No suggestions at all
Explain                ML summarizes recon only, no action suggestions  
Suggest Safe           Rule-based suggestions for passive/low-risk only (DEFAULT)
Suggest Safe + ML      Above + ML ranks and adds suggestions (requires ML config)
Suggest All            Include exploit/post-exploit suggestions, manual approval required
Semi-Auto Chain        User approves a planned chain; Pwny executes with guardrails
                       (requires: scope defined, risk cap set, explicit acknowledgment)
```

The Semi-Auto Chain toggle should show this warning (exact text):

```
⚠️  SEMI-AUTO CHAIN MODE

You are enabling automatic execution of pre-approved module chains.
This WILL execute commands against target systems.

Before enabling, you must confirm:
☐ Workspace scope is defined and correct
☐ You have written authorization to test ALL targets in scope  
☐ You understand that module chains may:
    - Generate significant network traffic
    - Trigger intrusion detection systems
    - Cause service disruption on fragile targets
☐ You have set a risk level cap for automatic execution
☐ You accept full responsibility for all actions taken in this mode

[CANCEL]  [I understand — Enable Semi-Auto Chain]
```

### Technical Implementation Notes for Semi-Auto Chain

The chain runner needs:

```go
type ChainRunner struct {
    steps       []ChainStep
    breakpoints map[int]bool    // step index → stop and ask
    riskCap     RiskLevel        // don't auto-run above this
    autoStop    AutoStopConfig
}

type AutoStopConfig struct {
    StopOnFailure       bool
    StopOnSessionGained bool
    StopOnUnexpected    bool
    MaxRuntimePerStep   time.Duration
    DangerPatterns      []string
}
```

Each step produces a `ChainStepResult` which the next step's execution function can read:

```json
{
  "step": 2,
  "module": "auxiliary/scanner/smb/smb_version",
  "status": "succeeded",
  "output": {
    "os": "Windows Server 2012 R2",
    "smb_version": "SMBv2"
  },
  "available_to_next_step": true
}
```

Step 3 (`smb_enumshares`) can access step 2's output via `chain.context.previous.output`.

### Safety Features That Must Be Present Before Auto Mode Ships

1. **Scope enforcement at the job level**: Before any job runs, check target against workspace scope. This exists in the plan already.
2. **Risk metadata on every module**: Every module (Go, MSF, Python) must declare risk level.
3. **Auto-stop danger patterns**: Pwny should have a configurable list of output patterns that trigger auto-stop (e.g., "account locked", "connection refused by firewall", "access denied")
4. **Rate limiting**: Chains should not hammer targets. Minimum delay between steps configurable.
5. **Circuit breaker**: If N consecutive steps fail on same target, stop the chain.
6. **Audit trail**: Every auto-executed step must be logged as `auto_chain` event type with the full chain context, not just as a generic job.

### What ML Should Generate vs What Rules Should Generate

| Source | Generates |
|---|---|
| Deterministic rules | Module suggestions based on port/service fingerprint |
| ML | Summaries, host grouping, confidence ranking, chain ordering |
| Human | Final approval, risk override, chain customization |

ML should never be the sole source of an execution decision. It should always be ML → rules validate → human sees both → human decides.

## Decision Matrix

| Question | Answer |
|---|---|
| Should we add ML auto review (summarize, rank, suggest)? | Yes — in Phase 5/M7. Low risk. Always tagged as ML output. |
| Should we add auto-targeting (ML selects targets)? | Yes — as part of semi-auto chain in M8. User must approve the proposed target list before execution starts. |
| Should we add auto-chaining (sequential module execution)? | Yes — as semi-auto chain in M8. User approves the chain plan. Runtime guardrails enforce scope, risk caps, and auto-stop. |
| Should we add full autonomous exploitation? | No. It contradicts the project's identity, creates legal risk, and professional pentesters don't want it. |
| Should the toggle be one switch or multiple? | Multiple. "Auto Suggest" is a separate setting from "Semi-Auto Chain." They are different risk levels. |
| Should auto mode require a warning? | Yes. Semi-Auto Chain toggle must show a multi-checkbox acknowledgment dialog. It should also require scope to be defined. |
| Should auto mode be configurable per workspace? | Yes. Semi-auto behavior (risk caps, auto-stop conditions, step delays) must be workspace-level settings, not global. |
| What's the default mode? | "Suggest Safe" (rule-based, manual approval). Auto features are opt-in. |

---

## Summary

The plan is excellent. The "full auto" concept should be split into two features: **Auto Suggest** (ML reviews without execution) and **Semi-Auto Chain** (user approves a chain plan, Pwny executes with runtime guardrails). Full autonomous exploitation should not be built.

The warnings and guardrails I recommend:

1. Multi-checkbox acknowledgment dialog before enabling semi-auto chain
2. Scope must be defined before auto mode is available
3. Risk level cap per workspace (auto mode won't run high/critical risk modules)
4. Auto-stop on danger patterns, failures, or session gains
5. Step delay minimums to prevent flooding targets
6. Every auto action logged as `auto_chain` with full context
7. Auto mode disabled by default in team/shared workspaces
